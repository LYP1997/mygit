# 二开路线图与常见问题

## 1. 推荐的二开顺序

### 第一天：只读理解

- 跑通管理台和一个 Relay 请求；
- 阅读 `main.go`、`router/main.go`、`router/relay-router.go`；
- 跟踪 `controller.Relay` 到 `relay/common.GenRelayInfo`；
- 查看数据库中的 User、Token、Channel、Ability、Log；
- 在 `web/src/routes` 找到一个页面和它的 feature。

### 第二天：做一个小改动

建议先做一个不改变计费和数据库的管理台字段或只读接口，完整走一遍：路由 → 中间件 → Controller → Service → 前端 → 测试。

### 第三天：做真实业务改造

根据目标选择：

- 新上游：从 `relay/channel/adapter.go` 和相近渠道开始；
- 新异步任务：先决定 Go TaskAdaptor 还是 JavaScript Plugin；
- 新页面：从 `web/src/routes`、`features` 和共享组件开始；
- 新计费：先读计费规则，再画预扣到结算的完整链路；
- 新权限：先梳理 session/PAT/Relay Token 三条路径，再改路由和服务端授权。

## 2. 常见问题

### 为什么我改了前端但后端启动看不到变化？

后端嵌入的是 `web/dist`。开发时用 Rsbuild dev server；生产或 `go run .` 前要重新 `bun run build`。

### 为什么新 API 返回 404？

确认路由注册函数确实被 `router.SetRouter` 调用，方法、路径和通配符没有冲突，并且没有被 `FRONTEND_BASE_URL` 的 NoRoute 重定向覆盖。

### 为什么 API Token 可以访问管理接口？

管理台接口使用 dashboard session 或声明过 scope 的 PAT；Relay Token 和管理台 PAT 是不同凭据。检查 `middleware/auth.go`、`middleware/access_token_routes.go` 和对应路由规则。

### 为什么请求能进来但没有渠道？

通常是 Token 用户分组、请求模型、Channel 分组、Ability、渠道状态、模型映射或缓存不一致。先看 `service/channel_select.go`，再看 `model/channel*.go`。

### 为什么渠道重试后扣费不对？

检查 `RelayInfo` 是否在每个 attempt 正确重置，计费 session 是否复用，预扣是否覆盖新渠道价格，实际 usage 是否只结算一次，以及失败后是否重复退款。

### 为什么新插件上传成功但请求没有进入？

检查插件是否 enabled、manifest 的 model/protocol 声明是否匹配、路由是否冲突、渠道是否绑定插件，以及 Registry 是否已经发布新 generation。

### 为什么插件明明返回 usage，价格还是不对？

检查 `usageSchema` 的 key、unit、description、usage profile、表达式引用和 Host 对 usage fact 的边界校验。usage quantity、价格和最终 quota 不是同一个概念。

### 为什么直接修改 Model 结构体还不够？

项目需要兼容已有数据库。必须同时考虑 AutoMigrate、自定义迁移、三种数据库、重复启动、旧数据和索引约束。

### 为什么不能直接在 Relay channel 里扣余额？

渠道适配器只负责上游通信和用量解析；扣费是跨重试、失败、订阅、Token 和日志的业务生命周期，应由 `BillingSession` 和 `service` 统一处理。

## 3. 代码评审自检

- [ ] 改动位置符合 router/controller/service/model/relay 边界。
- [ ] 没有绕过已有共享组件、HTTP client、JSON wrapper、错误和权限机制。
- [ ] 没有破坏根模块、relaykit、tokenkit 的独立性。
- [ ] 未修改受保护的项目身份、版权、署名和元数据。
- [ ] 涉及认证时检查了会话、Token、权限、重放、过期、限流和审计。
- [ ] 涉及计费时检查了边界、预扣、结算、退款和日志。
- [ ] 涉及数据库时完成 SQLite/MySQL/PostgreSQL 验证。
- [ ] 涉及前端时检查了复用、i18n、格式化、可访问性和 build。
- [ ] 测试保护的是用户可观察行为或跨模块契约，而不是实现细节。
