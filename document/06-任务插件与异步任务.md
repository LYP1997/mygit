# 任务插件与异步任务

## 1. 两种任务实现

### Go 原生任务适配器

目录通常在 `relay/channel/task/` 或具体渠道目录，接口定义在 `relay/channel/adapter.go` 的 `TaskAdaptor`。适合复杂、稳定、需要强类型和高性能的供应商接入。

### JavaScript Task Plugin

- 插件源码：`plugins/tasks/<key>/plugin.js`；
- 内置插件嵌入：`plugins/embed.go`；
- 运行时：`pkg/jsplugin/`；
- 数据库上传、启用、禁用、版本和校验：`controller/task_plugin.go`、`model/task_plugin.go`；
- Host Protocol 路由：`router/task-plugin-protocol-router.go`；
- 原生动态路由：`router/plugin-router.go`；
- 任务执行和轮询：`service/task_polling.go`、`service/task.go`。

## 2. 插件开发必读材料

修改或新增插件前完整阅读：

- `docs/plugin-api/v1.md`：API v1 行为和限制；
- `docs/plugin-api/v1.schema.json`：manifest 校验；
- `docs/plugin-api/v1.d.ts`：类型和 Hook 契约；
- `plugins/tasks/*/plugin.js`：已有实现；
- `pkg/jsplugin/engine.go`、`registry.go`、`routing.go`：Host 生命周期和路由。

## 3. 插件 manifest 的核心概念

~~~js
export const meta = {
  apiVersion: 1,
  key: "vendor",
  name: "Vendor",
  version: "1.0.0",
  author: { name: "Author" },
  description: { en: "...", zh: "..." },
  models: ["vendor-model"],
  fetchMode: "per_task",
  routes: [...],
  protocols: [...],
  usageSchema: {...},
};
~~~

- `routes`：插件拥有的原生 URL；
- `protocols`：声明接入 Host Protocol，不复制 Host URL；
- `fetchMode`：单任务轮询或批量轮询；
- `baseUrl`、`allowedHosts`：上游目标和 SSRF/凭据接收边界；
- `usageSchema`/`usageProfiles`：Host 计费字段定义；
- `upstreams`：供应商 API 或另一个安装了相同插件的网关。

## 4. 插件任务生命周期

~~~text
decodeRequest
 → buildSubmitRequest
 → Host 发起上游请求
 → parseSubmitResponse / parseSubmitEventDelta
 → 创建 model.Task
 → extractUsageOnSubmit（如适用）
 → service/task_polling.go 轮询
 → buildQueryRequest / parseTaskResult
 → extractUsageOnComplete
 → 更新任务和产物
 → 结算/退款/消费日志
 → render 给客户端
~~~

同步任务也必须考虑：客户端断开、上游超时、任务重复轮询、插件版本变化、历史任务继续执行和结果产物访问。

## 5. 插件计费规则

插件返回的是 usage quantity，不是直接返回价格。`usageSchema` 的数字字段：

- `unit` 表示 `second`、`count`、`token` 或 `credit`；
- `description` 要说明“计费对象 + 单价”语义，例如 `Image generation unit price`；
- 单位放在 `unit`，不要把价格、协议限制和实现细节写进描述；
- 用量事实必须非负、有限并符合 Host 边界；
- 插件必须从实际发送给上游的请求和上游结果推导事实，不能相信客户端任意传入的 billing 数字；
- 任务提交、完成、失败都要检查预扣和最终结算是否一致。

修改插件数值计费前，要同时查看 `.agents/rules/billing.md` 和 `setting/billing_setting/` 的现有规则。

## 6. 原生路由和 Host Protocol 的选择

使用原生路由：

- 供应商 URL 和请求结构无法抽象成 Host Protocol；
- 需要自定义查询、提交、渲染路径；
- 请求路径属于插件自己的命名空间。

使用 Host Protocol：

- 希望客户端使用统一的 OpenAI Responses、Video 或 Image API；
- 插件只负责 decode、上游请求、解析和 render；
- 希望复用 Host 的认证、任务、产物、路由和计费骨架。

路由冲突由 Host 预检；上传插件时要处理编译失败、manifest 不合法、路由冲突、版本和 SHA-256 校验。

## 7. 如何调试插件

优先使用：

- `new-api plugin ...` CLI：查看 `main.go` 对 `plugin` 子命令的分支；
- `pkg/jsplugin/*_test.go`：运行时和注册表测试；
- `controller/task_plugin*`：上传、启停、路由和管理 API 测试；
- `plugins/*_test.go`：供应商响应解析测试；
- `model/task_plugin_test.go`、`model/task_test.go`：持久化和任务状态测试。

调试时区分三类问题：

1. manifest/编译问题：插件还没有进入 Registry；
2. 路由/绑定问题：请求没有进入插件；
3. 上游/解析问题：已进入插件但请求、轮询或 usage 错误。
