# 数据模型、计费、认证与安全

## 1. 主要数据对象

| 对象 | 代码入口 | 作用 |
| --- | --- | --- |
| User | `model/user.go` | 用户、角色、分组、余额、统计和状态 |
| Token | `model/token.go` | API 调用凭据、额度、模型限制、IP 限制和状态 |
| User session | `model/user_session.go`、`service/auth_session.go` | 管理台登录会话、撤销和版本 |
| Access Token/PAT | `model/user_access_token.go`、`middleware/access_token_routes.go` | 受作用域限制的管理台访问凭据 |
| Channel | `model/channel.go` | 上游渠道、类型、Key、Base URL、模型和分组 |
| Ability | `model/ability.go` | 渠道可用模型及能力 |

| Task | `model/task.go` | 异步任务、状态、上游任务 ID、结果和私有计费上下文 |

| Casbin rule/role | `model/casbin_rule.go`、`service/authz/` | 细粒度权限和资源授权 |

## 2. 认证链路

### 管理台

~~~text
Authorization Bearer
 → middleware.UserAuth/AdminAuth/RootAuth
 → service.ParseDashboardAccessToken
 → ValidateLoginSession 或 PAT 查询
 → 用户状态、角色、Token scope、权限校验
 → controller 读取 c.Context
~~~

相关入口：`middleware/auth.go`、`service/auth_session.go`、`model/user_session.go`、`service/authz/`。

### Relay Token

~~~text
Authorization / x-api-key 等请求头
 → middleware.TokenAuth
 → model.Token 查询/缓存
 → Token 状态、IP、用户状态、额度和模型限制
 → c.Set(token_id/token_key/id/...)
~~~

不要把管理台 PAT 当作 Relay API Token，也不要让前端验证替代服务端鉴权。

## 3. 计费模型

一次请求的核心对象是 `relay/common.RelayInfo` 和 `service.BillingSession`：

~~~text
请求验证
 → 估算价格/用量
 → PrepareRequestBilling
 → 预扣 Token 与钱包/订阅额度
 → 上游执行
 → 从 usage、响应或任务结果得到实际用量
 → SettleBilling：补扣或退款差额
 → 失败路径 Refund
 → consume/task log
~~~

重点文件：

- `types/price_data.go`：价格和比例数据；
- `relay/request_billing.go`：Relay 预扣入口；
- `service/billing_session.go`：预扣、结算、退款生命周期；
- `service/quota.go`、`service/text_quota.go`：文本和通用 quota；
- `service/image_billing.go`：图片计费；
- `service/task_billing.go`：任务计费；
- `service/tiered_settle.go`：表达式/分层计费；
- `service/log_info_generate.go`、`service/responses_usage.go`：用量和日志信息；
- `setting/billing_setting/`、`pkg/billingexpr/`：价格表达式和内置价格。

计费改造必须维护以下不变量：

- 计费数量先验证、再进入倍率和 quota 计算；
- 不能因为整数溢出或 NaN 产生负扣费；
- 预扣失败不能留下部分扣费；
- 结算只调整差额，不能重复提交；
- 失败和客户端中断要按实际状态决定退款；
- 异常饱和要进入管理员日志和告警；
- `PriceData.OtherRatios` 使用安全写入方法，不直接篡改内部 map；
- 图片、视频时长、批次数、Token 上限等倍率字段都要限制上界。

如果只是修改页面显示价格，也要确认没有误改真实计费价格；如果修改真实价格，必须同步价格配置、缓存、日志和回归测试。

## 4. 日志和敏感数据

日志既用于用户查看，也用于管理员排查。写日志时：

- 不写密码、验证码、恢复码、私钥、完整 API Key、可用会话 Token；
- 需要关联请求时使用 request ID、Token fingerprint 或脱敏引用；
- 计费异常写管理员可见的结构化信息；
- 不要把上游完整响应或请求头无条件写入日志；
- 记录足够的模型、渠道、错误类别、重试和耗时信息以便排查。

## 5. 多数据库和多节点

主库支持 SQLite、MySQL、PostgreSQL；日志库还可配置 ClickHouse。相关代码会通过 `common.UsingMainDatabase` / `UsingLogDatabase` 分支处理差异。

多节点部署通常需要：

- 共享主数据库；
- 共享 `SESSION_SECRET` 和有效的 `CRYPTO_SECRET`；
- 使用共享 Redis 才能共享部分限流和缓存状态；
- 配置节点名以便审计和排障；
- 由系统任务的数据库租约避免重复执行。
