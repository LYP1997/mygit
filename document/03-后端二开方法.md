# 后端二开方法

## 1. 新增一个管理 API

建议步骤：

1. 在 `router/api-router.go`、`router/dashboard.go` 或对应专用 Router 中注册路径。
2. 给路由挂上正确的 `UserAuth`、`AdminAuth`、`RootAuth`、`RequirePermission`、限流、审计和缓存中间件。
3. 在 `controller/<domain>.go` 中做绑定、参数校验和响应编排。
4. 复杂业务放入 `service/<domain>.go`；不要把事务、权限和多表业务全部写在 Controller。
5. 数据库读写放入 `model/<entity>.go`，跨数据库行为在 `model/main.go` 和测试中确认。
6. 使用项目统一的 `common.ApiSuccess`、`common.ApiError`、`common.ApiErrorT` 等响应函数。
7. 前端需要使用时，在 `web/src/features/<feature>/api.ts` 增加调用和类型。

最小入口关系：

```go
// router/dashboard.go 或对应路由文件
group.GET("/resource", middleware.AdminAuth(), controller.ListResource)

// controller/resource.go
func ListResource(c *gin.Context) {
    items, err := service.ListResource(c)
    if err != nil {
        common.ApiError(c, err)
        return
    }
    common.ApiSuccess(c, items)
}
```

实际代码还需要补充分页、权限、审计、错误码、i18n 和测试；以上只是入口关系。

## 2. 修改已有业务

按以下路径排查：

```text
路由是否进入？
  → 中间件是否提前 Abort？
    → Controller 是否正确解析？
      → Service 是否做了业务决策？
        → Model 是否读写正确？
          → 前端是否按真实 API 响应处理？
```

推荐用 `rg` 查找：

```powershell
rg -n "目标函数|目标路径|数据库字段|错误文本" router controller service model web/src
```

一个已有功能可能同时有：管理台接口、Relay 接口、后台任务、前端页面和日志展示。修改前先画出调用链，不要只看同名函数。

## 3. 新增或修改数据模型

典型位置：

- 结构体和 CRUD：`model/<entity>.go`；
- 数据库连接和迁移入口：`model/main.go`；
- 公共时间和 JSON 字段：`model/db_time.go` 及相邻实现；
- 锁：`model/locking.go`，标准行锁使用 `lockForUpdate(tx)`；
- 缓存：`model/*_cache.go`、`common` 缓存能力；
- 业务调用：`service/<domain>.go`。

数据库修改必须考虑 SQLite、MySQL、PostgreSQL，同时检查：

- 新数据库首次启动；
- 旧数据库升级；
- 启动迁移两次是否幂等；
- 索引、唯一性、已有数据是否保留；
- 日志库是否共享了同一段迁移逻辑；
- SQLite 是否需要单独的 `ADD COLUMN` 路径；
- 是否误用了 MySQL 或 PostgreSQL 专属 SQL。

不要直接把 `AUTO_INCREMENT`、`SERIAL` 或某个数据库专属 JSON 类型写进通用模型。

## 4. JSON、错误和日志

根模块的 JSON 编解码统一使用：

```go
common.Marshal(v)
common.Unmarshal(data, &v)
common.UnmarshalJsonStr(s, &v)
common.DecodeJson(reader, &v)
```

`encoding/json` 的类型可以作为类型引用，但业务代码不应直接调用标准库的 Marshal/Unmarshal。

管理台 API：

- 返回英文源文本或稳定错误码；
- 前端翻译英文 key；
- 需要参数化时使用 `common.NewMessage`；
- 后端日志行使用 `common.LogText`；
- 认证审计不得写入密码、验证码、恢复码、私钥或可用 Token。

## 5. 新增配置

配置优先按领域放入 `setting/<domain>/`，全局环境变量读取和默认值集中在 `common/env.go` 或现有 setting 配置中。建议：

1. 在 `.env.example` 增加说明；
2. 解析、默认值、合法范围和敏感信息处理集中实现；
3. 管理台可修改的配置走 `model.Option` 或已有设置服务；
4. 多节点配置要明确是数据库配置、环境变量配置还是节点本地配置；
5. 为错误值、缺失值、热更新和重启恢复补测试。

## 6. 修改认证和权限

入口分两类：

- 管理台：`middleware/auth.go`、`service/auth_session.go`、`model/user_session.go`、`service/authz/`；
- Relay Token：`middleware/auth.go` 中的 `TokenAuth`、`model/token.go` 和 Token 缓存。

修改认证流程前必须检查会话轮换、撤销、过期、Cookie、Origin/CSRF、防暴力尝试、错误枚举、审计脱敏和重新认证。权限不要只加前端按钮判断，服务器路由和业务层都要守住边界。

## 7. 测试放置原则

- Controller 路由、权限和响应契约：优先扩展 `controller/*_test.go` 或 `router/*_test.go`。
- Service 业务规则：扩展对应 `service/*_test.go`。
- Model、迁移和数据库兼容：扩展 `model/*_test.go`。
- Relay 协议转换：扩展对应 adaptor/handler 测试和 `relaykit` golden 测试。
- 小功能不要在 controller、service、model 各复制一套相同测试。
