# 启动流程与请求链路

## 1. 启动入口

程序从 `main.go:main` 开始。执行顺序可以概括为：

```text
main
 ├─ plugin 子命令检查：new-api plugin ...
 ├─ InitResources
 │   ├─ godotenv.Load(.env)
 │   ├─ common.InitEnv
 │   ├─ ratio_setting.InitRatioSettings
 │   ├─ service.InitHttpClient
 │   ├─ model.InitDB / authz.Init
 │   ├─ model.CheckSetup / InitOptionMap
 │   ├─ model.InitLogDB
 │   ├─ common.InitRedisClient
 │   ├─ i18n.Init
 │   ├─ oauth.LoadCustomProviders
 │   └─ service.StartAuthArtifactCleanup
 ├─ 初始化渠道缓存、价格缓存和 WebSocket 订阅
 ├─ 启动系统任务、订阅重置、实例上报、插件同步等后台任务
 ├─ 创建 gin.Engine 和全局中间件
 ├─ router.SetRouter
 ├─ ListenAndServe
 └─ 收到 SIGINT/SIGTERM 后优雅关闭
```

启动行为要看：

- `main.go`：入口和后台任务；
- `common/env.go`：环境变量解析；
- `model/main.go`：主库、日志库和迁移；
- `router/main.go`：所有路由聚合；
- `service/system_task.go`：系统任务调度。

后端会通过 `//go:embed web/dist` 嵌入前端构建产物，所以生产启动前必须准备 `web/dist`。

## 2. 路由注册顺序

`router.SetRouter` 依次注册：

1. `SetApiRouter`：管理台和通用 `/api` 接口；
2. `SetDashboardRouter`：控制台业务接口；
3. `SetRelayRouter`：`/v1`、`/v1beta`、`/mj` 等 AI API；
4. `SetTaskPluginProtocolRouter`：插件声明的 Host Protocol 路由；
5. `SetVideoRouter`、`SetTaskRouter`：视频和异步任务相关路由；
6. `SetPluginRouter`：插件原生动态路由；
7. `SetWebRouter`：静态前端和 SPA fallback。

新增路由时先判断属于哪一类，不要把管理 API、Relay API 和插件原生路由混在一起。

## 3. 一次文本 Relay 请求

以 `POST /v1/chat/completions` 为例：

```text
请求
 │
 ├─ CORS / 解压 / BodyStorageCleanup / StatsMiddleware
 ├─ RouteTag("relay")
 ├─ SystemPerformanceCheck
 ├─ TokenAuth：验证 API Token、IP 限制、用户状态和余额相关上下文
 ├─ ModelRequestRateLimit
 ├─ Distribute：生成请求分发上下文
 └─ controller.Relay(..., RelayFormatOpenAI)
      ├─ helper.GetAndValidateRequest：解析并校验 DTO
      ├─ relaycommon.GenRelayInfo：建立本次请求的统一上下文
      ├─ relay.PrepareRequestBilling：计算并预扣
      ├─ 循环重试
      │   ├─ getChannel / service.SelectChannelForRequest
      │   ├─ PrepareTieredBillingForSelectedGroup
      │   ├─ 选择 relay/channel/<provider> 适配器
      │   ├─ ConvertOpenAIRequest
      │   ├─ GetRequestURL / SetupRequestHeader / DoRequest
      │   ├─ DoResponse：普通响应或 SSE 流转换
      │   ├─ 计算 usage 和实际 quota
      │   ├─ service.SettleBilling
      │   └─ 写消费日志、渠道统计和请求策略结果
      └─ 失败时按策略重试、封禁/降级渠道、退款并返回统一错误
```

核心文件：

- 路由：`router/relay-router.go`；
- 总入口：`controller/relay.go` 的 `Relay`；
- 请求验证：`relay/helper/valid_request.go` 和 `relay/helper/common.go`；
- 请求上下文：`relay/common/relay_info.go`；
- 选渠道：`service/channel_select.go`；
- 计费生命周期：`relay/request_billing.go`、`service/billing_session.go`；
- 普通文本：`relay/compatible_handler.go`；
- Claude/Gemini/Responses：对应的 `relay/*_handler.go`；
- 统一适配器接口：`relay/channel/adapter.go`。

## 4. 一次管理台请求

```text
web/src/features/<feature>/api.ts
        │
        ▼
web/src/lib/http-client.ts / api.ts
        │
        ▼
/api/... → router/api-router.go 或 router/dashboard.go
        │
        ▼
middleware.UserAuth / AdminAuth / RootAuth / RequirePermission
        │
        ▼
controller/<feature>.go
        │
        ▼
service/<feature>.go
        │
        ▼
model/<entity>.go
        │
        ▼
common.ApiSuccess / ApiError 返回稳定 API 契约
```

管理台的 API 错误通常使用英文源文本或稳定错误码，前端再通过 i18n 翻译；不要只在前端添加提示而不补齐后端返回。

## 5. 重试和流式响应的注意点

- `RelayInfo` 会在一次请求的多次渠道尝试之间复用，但每次尝试需要清理流状态。
- 请求体通过 BodyStorage 支持重试；新逻辑不要把请求体一次读取后永久丢失。
- SSE 发生错误时，若响应头已经写出，不能再发送普通 JSON；应通过流格式写入错误事件和结束标记。
- WebSocket 的 Responses/Realtime 路径与普通 HTTP Relay 共用部分选择和计费逻辑，但响应写入方式不同。
- 影响计费的流式 usage 必须覆盖“正常完成、上游错误、客户端中断、重试”几种情况。

## 6. 后台任务

`main.go` 启动的后台能力包括：

- 渠道缓存同步和模型价格预热；
- 插件同步；
- Casbin 权限策略同步；
- 用量看板数据更新；
- Codex 凭据自动刷新；
- 订阅额度周期重置；
- 系统实例上报；
- 系统任务 Runner，负责渠道检测、模型更新和异步任务轮询。

新增周期任务优先接入 `service/system_task.go` 和 `controller/system_task_handlers.go` 的系统任务机制，避免在 `main.go` 直接创建无法去重、无法查看执行历史的 goroutine。
